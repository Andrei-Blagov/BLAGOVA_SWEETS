# BLAGOVA SWEETS: правила работы агента

Этот файл задаёт постоянный контекст для Codex, Cursor и других агентов. Подробное состояние проекта находится в docs/PROJECT_STATE.md, порядок работ — в docs/ROADMAP.md, передача работы в Cursor — в docs/CURSOR_HANDOFF.md.

## Цель

Создать качественный демонстрационный продукт кондитерской и небольшой кофейни в Паттайе на тестовых данных. Архитектура должна позволять быстро заменить тестовые товары, цены, фотографии и правила реальными данными перед запуском.

## Рабочая область

- Репозиторий: Andrei-Blagov/BLAGOVA_SWEETS.
- Рабочая ветка: prototype/pattaya-atelier.
- PR №1 остаётся черновиком до отдельного решения владельца.
- Не сливать ветку в main, не включать реальные платежи и не публиковать production без прямого запроса пользователя.
- Постоянный тестовый стенд разрешён только на `preview.blagovasweets.com`: отдельный Compose project, только demo-данные, `noindex` на трёх уровнях и без production-интеграций.
- Не добавлять секреты, ключи API, реальные пароли и персональные данные в git, логи, тесты или ответы.

## Источник истины

- Supabase — источник истины для каталога, цен, доступности, заказов, чата и базы знаний.
- Клиент не определяет цену, итог заказа или доступность; сервер пересчитывает и проверяет их транзакционно.
- Тестовые данные помечаются как demo и не смешиваются с будущими реальными данными.
- При расхождении старой документации с docs/PROJECT_STATE.md сначала обновить документацию, затем код.

## Обязательные правила разработки

- Сохранять RU/EN/TH; тайские тексты считать черновыми до проверки носителем.
- Все новые таблицы в открытой схеме защищать RLS и минимальными правами. service_role никогда не попадает в браузер.
- Изменения схемы выполнять новыми миграциями Supabase; применённые миграции не переписывать.
- Публичные операции должны иметь валидацию, rate limit и идемпотентность.
- Настройки товара и производственную нагрузку хранить структурированно, а не только текстовым описанием.
- Для загрузки фотографий использовать Supabase Storage с проверкой MIME, размера и прав; хранить alt-тексты и порядок изображений.
- Все изменения статуса заказа, цены, расписания и контента журналировать.
- Не считать запрос заказом до серверного сохранения. Не считать заказ подтверждённым до явного подтверждения менеджером.

## Проверка перед коммитом

1. Сверить задачу с docs/PROJECT_STATE.md и docs/ROADMAP.md.
2. Запустить только релевантные тесты, затем npm run build для изменений приложения.
3. Для БД проверить миграцию, RLS, конкурентный сценарий и повторный запрос.
4. Для Edge Functions проверить OPTIONS/CORS, ошибки, идемпотентность и отсутствие секретов в ответах.
5. Для Preview проверить healthcheck, HTTPS, `X-Robots-Tag`, отсутствие секретов в собранных файлах и возможность отката по `docs/PREVIEW_DEPLOYMENT.md`.
6. Обновить документацию, если изменились решения, схема, интеграции или порядок работ.
7. Оставить краткий handoff: commit SHA, сделано, проверки, риски, следующий шаг.

## Экономия лимита моделей

- GPT-5.6 Luna: механические правки, тестовые данные, локализации, форматирование, узкие CRUD-задачи.
- GPT-5.6 Terra: основная реализация Nuxt/Supabase, админка, интеграции и тесты.
- GPT-5.6 Sol: архитектура, транзакции, RLS, безопасность, платежи и неоднозначные ошибки.
- GPT-6 Astra: редкий финальный аудит особо сложного или критичного решения.
- Не повышать модель без конкретной причины. Если лимит Plus исчерпан, подготовить handoff по docs/CURSOR_HANDOFF.md.
