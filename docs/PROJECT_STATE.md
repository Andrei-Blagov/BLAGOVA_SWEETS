## Производственная вместимость

Сервер использует структурированные снимки и производственную нагрузку. Общий бюджет и пределы категорий проверяются одновременно, под блокировкой даты в одной транзакции. Состояние занятости учитывает всю БД, а не страницу админки.

Правила первой версии используют одновременно общий бюджет интервала и пределы категорий:

| Производственная сущность | Нагрузка | Предел на интервал |
| --- | ---: | ---: |
| Торт | 8 единиц | 4 торта |
| Набор конфет | 4 единицы | 4 набора |
| Комплект подарочных пряников | 1 единица | 8 комплектов |
| Капкейк или трайфл | 1 единица за штуку | 32 штуки суммарно на старте |

- Общий бюджет одного интервала: 32 единицы нагрузки.
- Эквивалентность: 8 капкейков/трайфлов = 1 торт = 2 набора конфет = 8 комплектов пряников.
- Минимальное количество капкейков/трайфлов в позиции: 1 штука.
- Заказ принимается, только если после его добавления не превышены общий бюджет и каждый категорийный предел.
- Примеры допустимых наборов: 2 торта + 2 набора конфет + 1 комплект пряников; 3 торта + 1 набор конфет + 1 комплект пряников; 1 торт + 3 набора конфет + 2 комплекта пряников.
- Праздничный или подарочный комплект расходует сумму нагрузки входящих компонентов. Для нестандартной позиции менеджер задаёт нагрузку вручную.
- Коэффициенты, общий бюджет и категорийные пределы редактируются владельцем в админке и сохраняются с версией.
- Availability API принимает состав корзины и возвращает, помещается ли именно этот состав в интервал.
- Подтверждение и перенос выполняют повторную транзакционную проверку под advisory lock.
- Pending-заявки с определённым составом удерживают место 60 минут по `reservation_expires_at`; срок настраивает владелец. Истечение освобождает ресурс без изменения статуса. Позднее подтверждение повторно проверяет вместимость.
- Решения владельца 05.10: подарки считают конфеты наборами по 6, пряники комплектами по 2; округление вверх по каждой категории внутри одного подарка, затем умножение на количество подарков. Праздничный комплект содержит один торт, выбранные капкейки по одному на гостя, пряники комплектами по 2 с округлением вверх.
- Неполная заявка из чата сохраняется без резерва. Перед подтверждением staff задаёт ненулевые категории нагрузки, основание оценки и согласованную цену для заявки без позиций. Нулевая/неизвестная нагрузка не допускается при подтверждении.
- Исторические 9 demo-заказов и 18 позиций сохранены без попыток восстановить утраченную конфигурацию. NULL означает неизвестную нагрузку; pending требует оценки. Подтверждённый заказ с неизвестной нагрузкой блокирует новые бронирования на пересекающееся время.
- Изменение правил создаёт новую строку `production_rule_versions` с автором и временем. Подтверждённые снимки и нагрузка не пересчитываются; новые пределы применяются при позднем подтверждении и переносе.

Локальный `supabase migration list --local` не подключился: отдельного PostgreSQL/Docker здесь нет; цепочка применена в изолированном PGlite. Две попытки проверить пересечение начала интервала при ожидании другой транзакции через connector не создали ожидания блокировки и не являются доказательством конкуренции. Блокировки вместимости и порядок дат сохранены; ранее проверенные реальные конкурентные сценарии этапа 2 не заменены однопоточным harness.

Перед окончательным закрытием этапа повторить на обновлённом Preview три исправленных сценария. PR №1 остаётся Draft, main и реальные платежи не менялись. Следующий этап после приёмки — операционная админка.

## Этап 3 — первый операционный блок (05.10)

Начат после исправлений приёмки этапа 2 (`2e3238b`). Объём: серверный поиск/фильтры/пагинация и метрики по всей выборке, загрузка карточки независимо от страницы, сохранённый состав/опции/нагрузка, понятная история и внутренние заметки с revision/idempotency. Календарь выдачи получает отдельную выборку даты вместо текущей страницы списка. Следующие блоки: назначения, worker/retry уведомлений и экспорт. Повторная ручная приёмка трёх исправлений этапа 2 остаётся отдельным пунктом; этап 2 не объявлен полностью закрытым.

Реализованы `staff_search_orders`, `staff_order_details` (public SECURITY INVOKER) и узкий staff-only API добавления заметки. Полнотекстовая проекция `private.order_search` с GIN обновляется транзакционно по сохранённым полям заказа/позиций. Дополнительно поддерживается поиск подстроки для неполного имени/контакта; этот fallback не использует GIN, дальнейшая оптимизация нужна при большой базе. Сортировка страниц фиксирована `created_at DESC, id DESC`. Список: 25 строк; календарь: собственные страницы по 100 с «Показать ещё». Фильтры: запрос, статус/активные, источник, получение и включительный диапазон дат выдачи в Asia/Bangkok. Метрики относятся ко всей текущей фильтрованной выборке, не к странице.

Карточка показывает сохранённые SKU, опции, компоненты, цену единицы, нагрузку/версию правил и серверный итог. Старые позиции без snapshot явно отмечены без восстановления по каталогу. История сравнивает последовательные revision: статус, перенос, оценка/основание, правила и резерв; старые события без конкретных различий остаются «Данные заказа обновлены». Внутренние заметки отделены от пожеланий клиента, содержат автора/время/revision, доступны только staff. Повтор ID с тем же автором/заказом/текстом возвращает одну заметку; другое содержимое отклоняется. Проверяется текущий revision под блокировкой заказа; заметка не меняет revision заказа, состав, цену, резерв и статус и допускается после завершения. Прямые browser INSERT/UPDATE/DELETE запрещены. Backend service_role сохраняет административные права; «неизменяемость» заметок относится к staff API.

Миграция `20261005151644_staff_order_workspace.sql` применена к demo Supabase. Проверены: 38 JS/security tests, все 20 миграций и три SQL-сценария в PGlite, typecheck, static build и built-assets scanner. `staff_order_workspace.sql` с 131 временной заявкой прошёл также в Supabase и откатил все данные: страницы >100, объединённый поиск имени/состава, номер/источник/получение/даты, детали/снимки/сумма, заметки/повторы/stale revision, owner/manager/отозванный/посторонний/anon. Security Advisor без новых замечаний. Новые блокировки касаются только узкого RPC заметок; настоящие одновременные вызовы заметок через connector отдельно не подтверждены. SQL serial regression не считается доказательством нескольких соединений.

Назначения ответственных, worker/retry уведомлений и экспорт реализованы следующим блоком, описанным ниже. Первый блок отдельно не означает завершение всего этапа 3. ## Этап 3 — назначения, повторы уведомлений и CSV (05.10)

Второй операционный блок реализован в рабочей ветке. Владелец назначает активного owner/manager; менеджер берёт свободный заказ на себя и освобождает свой. Чужое назначение менеджер не меняет. RPC блокирует заказ, проверяет revision и допускает идемпотентный повтор уже достигнутого назначения. Завершённые/отменённые заказы не переназначаются. Событие сохраняет ID и подпись ответственного на момент изменения; список, фильтр «Мои/Без ответственного» и карточка показывают назначения. Назначение не меняет состав, цену или нагрузку.

CSV экспортируется одним серверным запросом по всей применённой выборке, до 10 000 строк; большие выборки требуют уточнить фильтры. Экспорт менеджера и экспорт владельца по умолчанию не содержат имён/контактов/адресов клиентов и заметок. Владелец может явно включить имя, контакт и адрес; это право проверяется на сервере. Время — Asia/Bangkok, цены — сохранённые серверные суммы. CSV содержит UTF-8 BOM, CRLF, кавычки и защиту от формул таблиц во всех полях.

Уведомления подтверждения, переноса и отмены теперь сохраняют снимок сообщения и обрабатываются отдельным `notification-worker`: очередь, lease/CAS, восстановление через 5 минут, backoff, максимум 5 попыток, ручной повтор и журнал. Устаревшие события и повторы за пределами 23 часов после первой попытки требуют ручной проверки; старые неотправленные записи без снимка помещены в ручную проверку. `is_demo` никогда не вызывает Resend, отображается как «Демо: отправка проверена», без `sent_at`. Первичные уведомления intake пока остаются отдельным best-effort механизмом. Подробнее — `docs/email-notifications.md`.

Миграция `20261005155537_staff_assignments_and_delivery_worker.sql` применена к demo Supabase. Отдельно опубликованы enqueue-only `confirm-order` v3, `order-change` v2 и `notification-worker` v1. Platform script `supabase/ops/install_notification_schedule.sql` включает pg_cron/pg_net, хранит специальный токен и URL в Vault и запускает обработчик каждые две минуты. Проверка токена выполняется service-only RPC; browser JWT не предоставляет доступ к worker. Расписание не приостанавливалось. Живой Cron вернул HTTP 200 и обработал QA-письмо как simulated: истёкший lease восстановлен до второй попытки, письмо реально не отправлялось.

Проверки: 47 JS/security tests, 21 переносимая миграция и 4 SQL regression в PGlite, typecheck, static build и assets scanner. Новый SQL прошёл также в Supabase с rollback 105 заявок и временных staff: owner/manager, назначение/повтор/revision/история, 105 строк экспорта/приватность, снимок уведомления, повторный захват, истечение lease, старый ответ, backoff, ручной повтор/дубли, устаревшие переносы, лимит 5 попыток/23 часа и RLS. Advisor без новых security замечаний. Два одновременных вызова коннектора фактически исполнились последовательно (16:17:08–13 и 16:17:21 UTC): это не доказательство пересечения транзакций. Дополнительный тест с временной остановкой рабочего Cron был отклонён автоматической проверкой до выполнения; расписание осталось включено. Полноценная конкурентная приёмка и проверка новых форм в отдельной manager-сессии остаются пунктами приёмки.

Этап 3 не объявлен полностью принятым; функциональность трёх запрошенных направлений реализована. Повторная ручная приёмка трёх исправлений этапа 2 остаётся отдельным пунктом. PR №1 — Draft, main, production и платежи не менялись.

## Продолжение приёмки: проверка доступа

05.10 при открытии Preview воспроизведено длительное зависание «Проверяем доступ…», сохранившееся после reload. Корневая причина незавершившегося SDK/Auth-запроса не подтверждена. Консоль также показала два GoTrueClient с одним storage key; публичный каталог теперь имеет отдельный непостоянный ключ состояния, staff session key сохранён.

Вся проверка getUser + активного staff-членства ограничена 20 секундами. После тайм-аута доступ не открывается, появляется ошибка и кнопка повторной проверки; поздний ответ не записывает staff identity. Смена сессии, выход и более новая проверка инвалидируют предыдущую. Auth callback остаётся синхронным, серверный getUser и проверка роли в БД сохранены. Ни токены, ни роли в БД не создавались и не менялись.

Добавлены четыре регрессии: действующая роль/отозванный доступ, зависший Auth и поздний ответ, зависший staff lookup с AbortSignal, гонка проверок/выход. Всего 51 тест; SQL и worker не изменены. Ручная приёмка CSV, UI retry, manager-сессии и трёх исправлений этапа 2 остаётся открытой до проверки через действующую сессию на опубликованной версии.

CSV теперь подготавливается с постоянной ссылкой «Скачать CSV», а статус говорит о подготовке, не о подтверждённом сохранении на устройство. Смена применённых фильтров, owner-доступа, включения контактов или уход со страницы отзывают предыдущую blob-ссылку; поздний ответ старого экспорта не публикует файл. Добавлены две регрессии жизненного цикла и приватности, всего 53 теста. Получение CSV через действующую browser staff-сессию остаётся отдельной проверкой.
