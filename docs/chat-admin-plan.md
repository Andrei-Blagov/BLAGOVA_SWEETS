# Чат, заказы и админка — предложение для обсуждения

Статус: проектирование. Интеграции не подключены. Текущий сайт остаётся демонстрационным.

## Предлагаемый состав

- Существующий Nuxt: витрина, виджет чата и адаптивная админка.
- Supabase (предложение, требует выбора владельца): Postgres для заказов и переписки, Auth для сотрудников, Storage для файлов и pgvector для RAG.
- Серверный API: единая проверка заказов из формы, чата сайта и LINE; расчёт цены, резервирование производственной ёмкости и смена статусов.
- LINE Official Account + Messaging API: клиентский канал. Уведомления менеджеру и ответы из его LINE требуют отдельной маршрутизации, а не автоматического зеркалирования личного аккаунта.
- n8n: синхронизация с отдельным Google Calendar, уведомления, переиндексация утверждённых материалов. Основная запись заказа и проверка доступности остаются в серверном API и транзакции БД.

Для старта Supabase предпочтительнее отдельной векторной БД: реляционная БД нужна в любом случае. Pinecone можно рассмотреть отдельно, если измерения покажут ограничения поиска по знаниям. Выбор модели и embedding-модели не сделан.

## Путь заказа

1. Бот уточняет товар, количество, дату, способ получения, оформление и контакт. Поддерживает RU/EN/TH, переход к человеку и сохранение черновика диалога.
2. Сервер рассчитывает цену и проверяет ограничения. Модель не задаёт цену и не обещает свободный слот сама.
3. Клиент видит итоговую карточку и явно подтверждает отправку заявки.
4. Одна транзакция сохраняет заказ, позиции, историю статуса и событие синхронизации. Повторный запрос с тем же ключом не создаёт второй заказ.
5. Предложение для начального режима: заявка получает статус «Ожидает менеджера». Подтверждённым заказом она становится после проверки сотрудником. Автоподтверждение готового ассортимента можно включить позже по правилам.
6. n8n обрабатывает событие из очереди: создаёт/обновляет запись Google Calendar и уведомляет менеджера. Ошибка календаря не отменяет уже сохранённую заявку; видна в админке и повторяется без дублей.
7. Перенос и отмена обновляют существующее событие по сохранённому ID. Часовой пояс — Asia/Bangkok. База заказов остаётся главным источником состояния.

Календарь предлагается использовать для двух задач: срок готовности и выдача/доставка. Подтверждённые заказы и неподтверждённые заявки должны визуально отличаться. Состав записей и момент постановки обсуждаются с владельцем. Полные контакты и переписку не следует копировать в описание события: достаточно номера заказа и ссылки на защищённую карточку.

## LINE и работа менеджера

Единый inbox админки собирает диалоги сайта и LINE. Сотрудник принимает диалог; бот перестаёт автоматически отвечать до явного возврата. Сообщения и смена исполнителя фиксируются в истории.

Рекомендуемый первый этап: уведомления менеджеру в LINE с переходом к нужному диалогу админки. Если ответы должны отправляться непосредственно из LINE, нужен отдельный менеджерский интерфейс через бота: авторизованный LINE user ID, явный выбор диалога/номера заявки и подтверждённый адресат. Нельзя пересылать обычный ответ в «последний активный» клиентский чат: это создаёт риск отправки не тому человеку.

Диалог анонимного посетителя сайта не объединяется с LINE по имени или телефону. Продолжение между каналами требует явной безопасной привязки.

## Минимальная админка

| Раздел | Первый релиз |
| --- | --- |
| Заказы | Список/доска статусов, детали, позиции, изменение даты и состава, ответственный, история, отдельный статус оплаты |
| Диалоги | Сайт + LINE, назначение менеджера, пауза бота, заметки, быстрые ответы, ссылка на заказ |
| Производство | Заказы на день, сроки, лимиты загрузки, выходные и заблокированные интервалы |
| Каталог | Товары, варианты, цены в THB, доступность, сроки подготовки, фотографии, состав и проверенные аллергены |
| Знания бота | Черновики, проверка/публикация, источники, версии, язык, дата актуальности, тестовые вопросы и история индексации |
| Интеграции | Состояние LINE/Calendar, ошибки и повторная синхронизация, без отображения секретов |
| Сотрудники | Владелец, менеджер, кондитер; доступ только к необходимым данным и журнал действий |

После первого релиза: повторные заказы, сегменты B2B, учёт расходов, рецептуры/себестоимость, аналитика диалогов и отказов. Не включать эти задачи в первый релиз автоматически.

## База знаний и RAG

Материал проходит путь «Черновик → Проверен владельцем → Опубликован → Проиндексирован». Клиентский бот ищет только опубликованное. Черновые цены, старые условия, внутренние инструкции и персональные данные не попадают в общий клиентский индекс.

Цены, остатки, доступные слоты, статусы заказов и оплата читаются через серверные инструменты из структурированных таблиц. RAG используется для описаний вкусов, инструкций по получению/хранению, правил заказа и FAQ. При отсутствии утверждённого ответа бот сообщает об этом и передаёт вопрос менеджеру. Особенно нельзя выводить гарантии отсутствия аллергенов из неполного текста.

Качество проверяем набором вопросов на RU/EN/TH: правильность ответа, правильность найденного источника, устаревшие/неизвестные условия и передача менеджеру. Перед выбором embedding-модели проверяем её на тайском и русском материале.

## Технические границы

Текущая публикация — static Nuxt. Секреты LINE, модели и Google нельзя добавлять в браузер. Потребуется отдельный серверный API либо Edge Functions. Конкретное размещение выбирается после выбора проекта Supabase и проверки серверного окружения.

В предлагаемой схеме: products/variants, customers/channel-identities, conversations/messages, order-drafts/orders/order-items/status-history, capacity/slots, knowledge-documents/versions/chunks, staff-members, integration-outbox/calendar-links. Это логическая схема, не выполненная SQL-миграция.

Перед открытием реальным клиентам обязательны проверка webhook-подписи LINE, авторизация сотрудников и ограничение доступа к данным, защита от повторных событий, тестирование конкурентного бронирования, лимиты чата, проверка резервного копирования и тестовые интеграционные сценарии. Ни одна интеграция пока не считается работающей.
