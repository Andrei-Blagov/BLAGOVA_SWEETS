# Supabase: структура базы BLAGOVA SWEETS

Целевой проект: `upmmgdshvgyqivfsyqju` — BLAGOVA_SWEETS_Frankfurt, eu-central-1.
Этап: схема и права доступа готовы; сайт и демо-админка ещё не подключены.
Пользователи сотрудников не созданы. Временные данные проверки отменены через ROLLBACK.

## Модель доступа

- Посетитель anon: чтение опубликованных товаров, активных вариантов и проверенных активных начинок. Демо-товары могут публиковаться, но должны быть явно помечены в интерфейсе.
- Авторизованный пользователь без активного staff_members: тот же открытый каталог, без доступа к заказам, контактам, чату и знаниям.
- Менеджер: чтение операционных данных, каталога и знаний. Изменения заказа и отправка сообщения будут выполняться через будущий серверный API с проверкой роли.
- Владелец: дополнительно может редактировать каталог и материалы знаний.
- Роли сотрудников назначаются только доверенным сервером/администратором. Саморегистрация не даёт доступ в админку.
- Запись заказов, контактов, сообщений, истории и очереди закрыта клиентским ролям. service_role разрешён только на сервере; он обходит RLS, поэтому будущий API обязан проверять сотрудника и входные данные.
- Владелец тоже не может изменить состав staff_members непосредственно из браузера.

## Целостность данных

- Деньги: целые сатанги; 1450 THB = 145000. Итог позиции вычисляет PostgreSQL. Итог заказа = сумма позиций + доставка; отдельного изменяемого total нет.
- В orders сохраняются контактные данные на момент заказа, независимо от последующего редактирования карточки покупателя.
- request_key уникален: повторный запрос не создаёт второй заказ. API должен обрабатывать конфликт как повтор операции.
- Даты: timestamptz; бизнес-часовой пояс Asia/Bangkok.
- Новая заявка всегда pending. Переходы: pending → confirmed → production → ready → completed; до завершения допустима отмена. Завершённый или отменённый заголовок заказа неизменяем.
- Подтверждение пустого заказа запрещено. Изменения заголовка автоматически увеличивают revision и создают order_events.
- Будущий API создаёт заголовок и позиции одной транзакцией, сверяет цены с каталогом, проверяет сроки/загрузку и согласованность состава. Изменения позиций должны обновлять заголовок в той же транзакции, чтобы история и синхронизация отражали изменение состава. Эти серверные операции пока не реализованы.
- После изменения текста, языка или заголовка материала публикация сбрасывается в draft, версия увеличивается. Публикация требует approved_by и approved_at.
- knowledge_chunks хранит версию исходного материала. Будущий поиск должен исключать устаревшие версии, внутренние материалы и черновики.
- Векторные поля, embeddings, модель и RAG-поиск ещё не настроены.

## Интеграции

Создание pending-заявки не запускает внешние операции.
При подтверждении и последующих изменениях заказа создаются задания для Google Calendar и LINE со статусом held.
Комбинация order_id + order_revision + provider уникальна.
Диспетчер, n8n-workflow, повторные попытки, блокировки, внешние идентификаторы и защита от доставки старых версий будут реализованы при подключении интеграций.
Сейчас задания никому не отправляются; в том числе демо-заказы не должны отправляться после включения диспетчера.
Google Calendar должен отражать подтверждённые заказы, а не использоваться как источник доступности производства.

## Миграции и проверка

SQL применён через Supabase MCP apply_migration. CLI Supabase отсутствовал в среде; файлы сохранены под точными версиями, возвращёнными list_migrations, без вымышленных временных меток.

- 20260918142143_blagova_foundation.sql
- 20260918142415_blagova_catalog_policies.sql
- tests/foundation_access.sql — транзакционный SQL-тест для пустой тестовой базы. Он создаёт временные auth-пользователи и бизнес-данные и завершает проверку ROLLBACK. Запускать целиком от административной роли, не на рабочей базе с реальными заказами.

Проверено: anon/посторонний/manager/owner, отсутствие самоповышения роли, отключение сотрудника, смена знаний на черновик, денежная арифметика, отрицательные цены, уникальность запроса, переходы статусов, история, отложенные задания при переносе и отмене.
После второй миграции тест повторён успешно.
Security Advisor: замечаний нет. Performance Advisor: только INFO о ещё не использованных индексах новой базы; предупреждение о пересекающихся SELECT-политиках устранено.
Документация уведомления об индексах: https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index
