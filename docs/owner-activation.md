# Первичная активация владельца

В целевом проекте Frankfurt создана private.owner_bootstrap. Адрес владельца, предоставленный в переписке, записан отдельно от миграции. На момент настройки аккаунта в auth.users с этим адресом нет; роль ещё не выдана.

## Поведение

- Только подтверждённый неанонимный пользователь с настроенным email получает owner.
- Привязка одноразовая: claimed_by и claimed_at фиксируются в одной транзакции под блокировкой строки.
- Существующие роли не перезаписываются; отключённый владелец автоматически не активируется повторно.
- private.assign_verified_owner — узкий SECURITY DEFINER trigger с пустым search_path. Вызов запрещён клиентским ролям и service_role; запускается при записи Auth в auth.users. При наличии auth.uid проверяется совпадение с изменяемым пользователем.
- Таблица настройки закрыта от клиентов и защищена RLS.
- Email не попадает в публичный клиентский код.
- Назначение роли не создаёт аккаунт и не отправляет письмо.

## Проверка

supabase/tests/owner_bootstrap.sql успешно проверяет неподтверждённого пользователя, другой адрес, подтверждение нужного адреса, однократность выдачи роли, сохранение отзыва доступа и отсутствие клиентского доступа. Временные записи отменены ROLLBACK.
Security Advisor: замечаний нет.
Тест рассчитан на пустую тестовую базу с существующей строкой owner_bootstrap; выполнять целиком административной ролью.

## Осталось для входа

Нужны создание/приглашение пользователя через Supabase Auth, проверка доставки email, настройка Site URL и разрешённых redirect URL, страница входа/callback и проверка роли в приложении.
Доступный Supabase MCP позволяет управлять SQL и Edge Functions, но не предоставляет Auth Admin или настройки Auth. Приглашения не отправлялись; пароль не запрашивался.
Демо-админка сайта всё ещё локальная и не подключена к Auth. Для реальных данных нельзя считать её защищённой данным триггером.
