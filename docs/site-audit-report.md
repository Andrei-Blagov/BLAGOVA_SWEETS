# Ревизия проекта · Pattaya Atelier (прототип)

**Дата:** 19 сентября 2026 (обновлено: стадия прототипа + уже выбранный Supabase)  
**Ветка:** `prototype/pattaya-atelier`  
**Стек:** Nuxt 4.2 · Vue 3.5 · TypeScript · Tailwind · **Supabase (уже в проекте)** · Edge Functions  
**Стадия:** концептуальный прототип — **не** готовый к наполнению коммерческий сайт

---

## 0. Исходные условия ревизии (обязательно читать)

### Supabase уже есть — рекомендации от этого отталкиваются

Выбор бэкенда **не открыт**. В проекте уже работают:

| Уже есть | Где |
| --- | --- |
| Проект Postgres (Frankfurt) + миграции | `supabase/migrations/*` |
| RLS, роли staff, каталог-таблицы, заказы, KB | foundation / policies / intake |
| Auth сотрудников + `/login`, `/admin` | `plugins/supabase.client.ts`, `useStaffAuth` |
| Публичный intake заявок | Edge Function `storefront-order` → RPC `receive_storefront_order` |
| Publishable-ключ в `runtimeConfig.public` | `nuxt.config.ts` |

**Следствие для рекомендаций:** не предлагать «внедрить БД», «выбрать CMS вместо файлов» или Prisma/MySQL как альтернативу. Нужно **дотянуть Nuxt-витрину и админ-формы до уже существующего Supabase**, убрать параллельные источники правды (TS-fixtures как единственный каталог, localStorage-KB, legacy Prisma) и при появлении данных писать **только** в этот контур.

Prisma/MySQL и файловые `/api/*` — наследие, не целевой путь.

На момент ревизии **ещё нет и не должно считаться дефектом**:

| Что отсутствует | Статус |
| --- | --- |
| Точное название бренда / wordmark | Не утверждено |
| Финальный каталог товаров | Нет — только демо-SKU |
| Реальные цены и себестоимость | Нет — иллюстративные цифры |
| Реальные фото товаров и пространства | Нет — концепт-изображения |
| Адрес, дата открытия, часы работы | Не определены |
| Контактные каналы (LINE, телефон, email боя) | Не зафиксированы |
| Утверждённая база знаний для чата/AI | Нет готового документа |
| Юр. тексты, аллергенная маркировка TH | Впереди |
| Платежи, LINE, Google Calendar, LLM | В планах |

**Цель ревизии смещена:** не «закрыть контентные дыры», а оценить, **насколько проект готов принимать данные по мере их появления**, и что перестроить, чтобы наполнение было безопасным, предсказуемым и без переписывания витрины.

Демо-контент в коде — это **fixtures для UX**, а не «недоделанный каталог».

## 1. Краткий вердикт

Прототип хорошо решает свою задачу: показывает **сценарии** (коллекция, подарок, праздник, кофейня, партнёры, корзина, заявка, staff-workspace) и **визуальный язык**. **Supabase уже выбран и частично подключён** (схема, RLS, Auth staff, Edge intake, `/admin`) — это сильная база, а не будущий этап.

Главный риск — не «нет БД» и не отсутствие бренда/цен/адреса, а **разрыв между витриной и уже существующим Supabase**: каталог и часть знаний всё ещё в коде/localStorage, пока заказы и staff уже в облаке. Когда появятся название, SKU, фото и контакты, их нужно класть в Supabase; иначе снова правка десятков Vue-файлов.

**Прогноз развития:** **довести потребление/запись к текущему Supabase** → наполнение данных → интеграции и SEO. Не проектировать второй бэкенд.

Приоритеты ниже переосмыслены:

- **P0 (каркас наполнения)** — без этого нельзя безопасно вносить реальные данные  
- **P1 (сценарии и операции)** — усиливает прототип и бету  
- **P2 (запуск и рост)** — только после утверждённого контента

## 2. Модель зрелости: что оцениваем на стадии прототипа

```
Сейчас                    Следующий шаг                         Когда данные готовы      Запуск
─────────────────────     ─────────────────────────────────     ────────────────────     ─────
UX + Supabase (частично) → Витрина/админ читают-пишут        → Наполнение в Supabase → Интеграции
Fixtures ещё в коде        уже существующие таблицы              + native QA TH           + платежи/SEO
Заказы уже в Supabase      + settings / Storage / сверка цен     + реальные ассеты        + index
```

| Вопрос ревизии | Правильный критерий на прототипе |
| --- | --- |
| Есть ли каталог? | Таблицы `products` / `variants` **уже в Supabase** — витрина их читает? |
| Есть ли бренд? | Есть ли запись settings в Supabase (или единый конфиг → тот же контур)? |
| Есть ли контакты/адрес? | Поля + UI «ещё не объявлено», без выдуманных фактов |
| Есть ли KB? | Модель `knowledge_documents` **уже есть** — чат читает published оттуда? |
| Можно ли заказывать? | Intake через Edge → Supabase уже работает для тестовых заявок |

Отсутствие утверждённого контента **не снижает** оценку прототипа. Снижает — если контент нельзя заменить без рефакторинга.

## 3. Карта системы (как есть)

### 3.1. Активный контур прототипа

| Слой | Роль сейчас | Готовность к наполнению |
| --- | --- | --- |
| Страницы витрины | Сценарии UX | Высокая — структура страниц годится |
| `data/atelier.ts` | Демо-SKU (fixture) | Временно ок; целевой source of truth — уже созданные таблицы каталога в Supabase |
| `useAtelier` / корзина | Клиентское состояние | Ок для прототипа |
| Edge `storefront-order` + RPC | Приём тестовых заявок **уже в Supabase** | Расширять (variant_id, сверка цен), не заменять |
| `/admin` + `$supabase` plugin | Staff workspace **уже на Auth/RLS** | Дописать UI наполнения каталога/settings |
| `/demo-admin` + chat localStorage | Песочница UX | Не путь наполнения; боевое — только Supabase |
| `knowledge_documents` | Модель + editor в `/admin` **уже есть** | Нет контента — ожидаемо; подключить чтение в чат |

### 3.2. Legacy (старый российский сайт)

Не относится к будущему наполнению Pattaya. Мешает тем, что создаёт **ложные «источники данных»** (`data/products.ts`, Prisma, старые компоненты). Для прототипа: изолировать/убрать, чтобы при появлении каталога никто не наполнял не тот слой.

### 3.3. Что в планах (не долг прототипа)

LINE, Calendar, AI/RAG, платежи, cookie/analytics, публичный SEO, партнёрский CRM, утверждённые юр. страницы — подключать **после** (или параллельно с) появлением стабильных бизнес-данных.

## 4. Сильные стороны именно как прототипа

1. **Сценарии важнее ассортимента** — gift-box, celebration, café, partners уже моделируют бизнес, даже без финальных SKU.  
2. **Честность** — demo-bar, `is_demo`, `noindex`, явные «адрес не определён» — правильная этика прототипа.  
3. **Мультиязычность заложена рано** — когда тексты утвердят, каналы RU/EN/TH уже есть.  
4. **Supabase-схема думает про деньги и роли** (minor units, RLS, revisions) — когда цены появятся, модель не придётся изобретать с нуля.  
5. **Knowledge pipeline уже стадийный** (draft → publish) — можно наполнять KB постепенно, не включая AI.  
6. **Intake заявок** уже отделён от «красивой витрины» — хороший задел под реальные заявки позже.

## 5. Главный вывод: проект нужно сделать «наполняемым»

Сейчас данные попадают в продукт тремя разными способами:

| Тип данных | Где лежит сейчас | Куда класть (уже на базе Supabase) |
| --- | --- | --- |
| Бренд (имя, tagline, лого) | Хардкод в Header/footer/titles | Новая таблица/строка `site_settings` в **этом же** проекте Supabase |
| Каталог, цены, lead time | `data/atelier.ts` (+ дубль legacy) | Уже существующие `products` / `product_variants` |
| Фото | `/public/prototype`, legacy-фото | **Supabase Storage** + URL в варианте/товаре |
| Адрес, часы, зоны | Текст в страницах | Поля в `site_settings` / `fulfillment_rules` (+ empty UI) |
| Контакты | Разрозненно / нет | Там же: LINE, email, phone — пустые до утверждения |
| Переводы UI | Inline `t(ru,en,th)` | Файлы i18n в Nuxt; тексты SKU — locale-поля в Supabase |
| База знаний | localStorage seed + пустые `knowledge_documents` | Уже существующие `knowledge_documents` (+ чат читает published) |
| Заявки с витрины | Уже Edge → Supabase | Расширять тот же intake, не плодить Nitro/JSON API |
| Юр. / privacy | Почти нет | Страницы Nuxt или документы в Storage; флаг публикации |

**Принцип:** витрина и админка опираются на **уже поднятый** Supabase. Fixtures — только fallback, пока published-рядов нет. Не вводить второй CMS/БД.

## 6. Рекомендации (наполнение поверх существующего Supabase)

Не «выбрать бэкенд», а **закрыть разрыв Nuxt ↔ Supabase**.

### 6.1. Каркас данных — P0

#### R1 · Паспорт сайта в Supabase (`site_settings`)

**Зачем:** бренд ещё не финален.  
**Что сделать:** миграция + RLS (чтение anon для публичных полей; правка — owner) в **текущем** проекте: `brandName`, `tagline`, `logoUrl`, `demoMode`, `contacts`, `locationStatus`. Хедер/`useHead` читают через `$supabase` или кэш на билде.  
**Почему:** одна запись в уже привычной админке/SQL, без смены стека.

#### R2 · Витрина читает уже существующий каталог Supabase

**Зачем:** товаров пока нет, но таблицы каталога и политики SELECT **уже развёрнуты**.  
**Что сделать:**
1. `data/atelier.ts` оставить как fixture/seed (`is_demo`), не как прод-источник.  
2. Страницы menu/product — `from('products')` / variants с фильтром published (anon RLS уже задуман). Пусто → fixture или empty-state.  
3. В `/admin` добавить CRUD каталога для owner (сейчас admin силён в заказах/KB, слаб в товарах).

**Почему:** первые реальные SKU вносятся в тот же Supabase, что и заказы — без нового сервиса.

#### R3 · Сверка цен в уже существующем Edge intake

**Сейчас ок** для демо: цена с клиента.  
**До реальных цен:** в `storefront-order` / `receive_storefront_order` принимать `variant_id` + quantity, цену брать из `product_variants` (таблица уже есть).  
**Почему:** усиливается текущий пайплайн, а не появляется параллельный orders API.

#### R4 · Медиа через Supabase Storage

**Что сделать:** bucket в том же проекте; поля URL у товара/варианта; статус `concept|final`. Legacy 31 MB из git убрать/изолировать.  
**Почему:** один аккаунт, те же RLS-привычки, что у остального staff-контура.

#### R5 · Контакты и локация — поля settings, не новый сервис

UI «ещё не объявлено» + заполнение `address` / `lineId` / hours в `site_settings`, когда данные появятся.  
Страницы café/delivery/footer только читают settings.

#### R6 · KB: дотянуть чат до уже существующей таблицы

Готового контента нет — нормально. Editor и `knowledge_documents` **уже в `/admin`**.  
**Сделать:** чат витрины ← published + public из Supabase (убрать опору на localStorage seed как источник правды). Пусто = честный ответ + handoff.  
AI/RAG — позже, поверх тех же документов (в схеме уже заложены chunks).

#### R7 · UI-словари в Nuxt; контент SKU в Supabase

Не дублировать описания тортов в Vue. Locale-поля каталога — в БД, где они и должны жить рядом с ценой.

#### R8 · Убрать конкурентов Supabase из ветки

Prisma/MySQL, файловые `orders.json` API, legacy `products.ts` — не развивать. Иначе при наполнении появятся «два каталога». Middleware, блокирующий старый `/api`, оставить до полной очистки.

---

### 6.2. Сценарии и продукт — P1 (можно делать без финального бренда)

#### R9 · Feature flag `demoMode` / `contentMode`

Управление дисклеймерами, demo-bar, ссылкой на `/demo-admin`, текстом «тестовая заявка».  
Когда данные появятся и бета закроется — один флаг, а не охота по строкам.

#### R10 · Empty-states на всех контентных поверхностях

Каталог пуст / KB пуста / контакты не объявлены / доставка «условия позже» — единый визуальный паттерн.  
Сейчас часть страниц уже честная; довести до системы, чтобы наполнение включало блоки «сами».

#### R11 · Партнёрская и контактная формы — контракт заявки без CRM

Форма cooperation сейчас noop — для прототипа ок.  
К наполнению: расширить **тот же** Edge/RPC-контур (или соседний RPC в том же проекте) типом `enquiry_type: partner|contact|order`. Не заводить отдельный CRM до реальной нагрузки.

#### R12 · Одна корзина, два контура админки с ясными ролями

- `/demo-admin` — песочница обучения UX.  
- `/admin` — **уже** подключено к Supabase: сюда пишут заказы, KB, (скоро) каталог и settings.  

Не сливать; в docs явно: «наполнение только через `/admin` + Supabase».

#### R13 · Handoff чата → уже существующие `conversations`

Кнопка «человек» должна создавать/обновлять запись в Supabase (как заявки из chat-order), видимую в `/admin`. Сейчас часть handoff остаётся в localStorage demo — это разрыв с уже работающим staff-контуром.

#### R14 · i18n routing позже, словари раньше

Префиксы `/en` `/th` — ближе к публичному запуску.  
Словари UI — раньше, чтобы утверждение брендовых формулировок не блокировалось вёрсткой.

#### R15 · Декомпозиция `admin` / `Chat` / CSS

Чтобы формы наполнения каталога и KB добавлять без боли в монолитных SFC.

### 6.3. Запуск — P2 (после появления данных)

Делать **когда** будут утверждены бренд, хотя бы стартовый ассортимент, канал связи и политика данных:

- SEO index, OG, JSON-LD (только на реальных Offer)  
- Cookie/PDPA, privacy page  
- Платежи + idempotent webhooks  
- LINE / Calendar dispatcher (jobs `held` уже задуманы)  
- Native review TH  
- CI e2e на критический путь  
- Owner activation и боевые staff-аккаунты  

**Не** блокировать прототип этими пунктами сейчас.

## 7. Прогноз развития (с учётом отсутствия данных)

### Фаза A — «Дотянуть витрину до уже существующего Supabase»

Цель: любой новый факт бизнеса сразу пишется в текущий проект Supabase, без ожидания «сначала выберем БД».

1. `site_settings` + чтение в Nuxt (R1), флаги demo (R9)  
2. Витрина ← published catalog (+ fixture fallback) (R2)  
3. Storage + чистка legacy-ассетов/Prisma (R4, R8)  
4. Контакты/локация в settings (R5)  
5. Чат ← `knowledge_documents` published (R6)  
6. Краткие гайды владельцу: куда в `/admin` класть бренд / SKU / FAQ  
7. Минимальный typecheck/CI  

**Результат:** логотип / 3 товара / LINE ID → внесли в Supabase через admin → сайт обновился. Новый бэкенд не нужен.

### Фаза B — «Закрытая бета с частичным контентом»

Когда есть черновой бренд и первые SKU (цены могут быть provisional):

1. Сверка цен в текущем Edge intake по `variant_id` (R3)  
2. Заявки уже в Supabase — усилить статусы/уведомления менеджеру  
3. Staff accounts (owner activation), наполнение KB  
4. Словари UI + native pass ключевых TH-строк  
5. Partner/contact через тот же Supabase-intake (R11)  
6. Handoff чата в `conversations` (R13)  

**Результат:** можно показывать избранным партнёрам/друзьям без стыда за «фейковый адрес», но ещё без публичного SEO.

### Фаза C — «Наполнение → публичный soft-launch»

Когда утверждены название, стартовое меню, фото, канал связи, базовые условия получения:

1. Снять/ослабить demo-chrome флагом  
2. Индексация, аналитика с consent  
3. Оплата или явный offline-payment  
4. LINE/Calendar по необходимости  
5. AI только поверх утверждённой KB  

**Результат:** прототипская оболочка становится сайтом без rewrite.

## 9. Чеклист «готовы принимать реальные данные»

Отмечать **до** появления контента, не вместо него:

- [ ] Бренд/tagline/лого из Supabase `site_settings` (или эквивалент в том же проекте)  
- [ ] Товар в `/admin` → published → виден на витрине **без** деплоя только ради контента  
- [ ] Цена заявки из `product_variants` в текущем Edge intake (к моменту реальных цен)  
- [ ] Фото в Supabase Storage, не пачками в git  
- [ ] Адрес/контакты: поля settings + корректный empty UI  
- [ ] Чат читает только published `knowledge_documents`  
- [ ] `demoMode` — один флаг (в settings)  
- [ ] Prisma/legacy-каталог не используются как путь наполнения  
- [ ] Инструкция владельцу указывает **только** `/admin` + Supabase

## 11. Итог

Прототип без финального бренда, каталога, цен, фото, адреса, контактов и KB — нормальная стадия. **Платформа данных уже выбрана: Supabase.**

Следующие работы — не «добавить базу», а **подключить витрину и формы наполнения к тому, что уже развёрнуто** (каталог, KB, Auth, Edge intake), убрать параллельные источники и при появлении фактов писать только туда.
