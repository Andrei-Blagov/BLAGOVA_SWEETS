# Ревизия проекта · Pattaya Atelier (прототип)

**Дата:** 19 сентября 2026 (обновлено с учётом стадии прототипа)  
**Ветка:** `prototype/pattaya-atelier`  
**Стек:** Nuxt 4.2 · Vue 3.5 · TypeScript · Tailwind · Supabase · Edge Functions  
**Стадия:** концептуальный прототип — **не** готовый к наполнению коммерческий сайт

---

## 0. Исходные условия ревизии (обязательно читать)

На момент ревизии **ещё нет и не должно считаться дефектом**:

| Что отсутствует | Статус |
| --- | --- |
| Точное название бренда / wordmark | Не утверждено |
| Финальный каталог товаров | Нет — только демо-SKU |
| Реальные цены и себестоимость | Нет — иллюстративные цифры |
| Реальные фото товаров и пространства | Нет — концепт-изображения |
| Адрес, дата открытия, часы работы | Не определены |
| Контактные каналы (LINE, телефон, email боя) | Не зафиксированы |
| Утверждённая база знаний для чата/AI | Нет готового документа |
| Юр. тексты, аллергенная маркировка TH | Впереди |
| Платежи, LINE, Google Calendar, LLM | В планах |

**Цель ревизии смещена:** не «закрыть контентные дыры», а оценить, **насколько проект готов принимать данные по мере их появления**, и что перестроить, чтобы наполнение было безопасным, предсказуемым и без переписывания витрины.

Демо-контент в коде — это **fixtures для UX**, а не «недоделанный каталог».

## 1. Краткий вердикт

Прототип хорошо решает свою задачу: показывает **сценарии** (коллекция, подарок, праздник, кофейня, партнёры, корзина, заявка, staff-workspace) и **визуальный язык**. Операционный каркас (Supabase, RLS, intake, staff roles) уже намечен правильно.

Главный риск на этой стадии — не отсутствие бренда/цен/адреса, а то, что **данные сейчас «зашиты» в код и размазаны по слоям** (`data/atelier.ts`, localStorage knowledge, хардкод в шаблонах, параллельный legacy-каталог РФ). Когда появятся настоящие название, SKU, фото и контакты, без слоя наполнения придётся править десятки файлов и снова деплоить витрину.

**Прогноз развития:** двигаться как **content-ready prototype** → **data-backed beta** → **launch**. Сначала контракты данных и единый источник правды, потом наполнение, потом интеграции и SEO.

Приоритеты ниже переосмыслены:

- **P0 (каркас наполнения)** — без этого нельзя безопасно вносить реальные данные  
- **P1 (сценарии и операции)** — усиливает прототип и бету  
- **P2 (запуск и рост)** — только после утверждённого контента

## 2. Модель зрелости: что оцениваем на стадии прототипа

```
Сейчас          Следующий шаг              Когда данные готовы         Запуск
─────────       ──────────────             ───────────────────         ─────
UX-оболочка  →  Контракты данных        →  Наполнение CMS/БД        →  Интеграции
Fixtures        + админ-формы ввода        + native QA TH              + платежи/SEO
Дисклеймеры     + feature flags            + реальные ассеты           + index
```

| Вопрос ревизии | Правильный критерий на прототипе |
| --- | --- |
| Есть ли каталог? | Есть ли **схема** товара/варианта/цены, куда потом положить SKU? |
| Есть ли бренд? | Вынесены ли имя, tagline, логотип в **один конфиг сайта**? |
| Есть ли контакты/адрес? | Есть ли поля + UI «ещё не объявлено», без выдуманных фактов? |
| Есть ли KB? | Есть ли модель документов + статусы draft/published (уже да в Supabase)? |
| Можно ли заказывать? | Можно ли проверить **поток заявки**, зная что заказ демо? |

Отсутствие утверждённого контента **не снижает** оценку прототипа. Снижает — если контент нельзя заменить без рефакторинга.

## 3. Карта системы (как есть)

### 3.1. Активный контур прототипа

| Слой | Роль сейчас | Готовность к наполнению |
| --- | --- | --- |
| Страницы витрины | Сценарии UX | Высокая — структура страниц годится |
| `data/atelier.ts` | Демо-SKU + строки RU/EN/TH | Низкая как source of truth — нужен перенос в БД/конфиг |
| `useAtelier` / корзина | Клиентское состояние | Ок для прототипа |
| Edge `storefront-order` + RPC | Приём тестовых заявок | Хороший каркас; цены пока с клиента (нормально до реальных цен) |
| `/admin` + staff Auth | Workspace | Готов принимать заказы/знания из БД |
| `/demo-admin` + chat localStorage | Песочница UX операций | Оставить как sandbox; не смешивать с боевым наполнением |
| `knowledge_documents` в Supabase | Модель KB | **Каркас есть**, документов ещё нет — это ожидаемо |

### 3.2. Legacy (старый российский сайт)

Не относится к будущему наполнению Pattaya. Мешает тем, что создаёт **ложные «источники данных»** (`data/products.ts`, Prisma, старые компоненты). Для прототипа: изолировать/убрать, чтобы при появлении каталога никто не наполнял не тот слой.

### 3.3. Что в планах (не долг прототипа)

LINE, Calendar, AI/RAG, платежи, cookie/analytics, публичный SEO, партнёрский CRM, утверждённые юр. страницы — подключать **после** (или параллельно с) появлением стабильных бизнес-данных.

## 4. Сильные стороны именно как прототипа

1. **Сценарии важнее ассортимента** — gift-box, celebration, café, partners уже моделируют бизнес, даже без финальных SKU.  
2. **Честность** — demo-bar, `is_demo`, `noindex`, явные «адрес не определён» — правильная этика прототипа.  
3. **Мультиязычность заложена рано** — когда тексты утвердят, каналы RU/EN/TH уже есть.  
4. **Supabase-схема думает про деньги и роли** (minor units, RLS, revisions) — когда цены появятся, модель не придётся изобретать с нуля.  
5. **Knowledge pipeline уже стадийный** (draft → publish) — можно наполнять KB постепенно, не включая AI.  
6. **Intake заявок** уже отделён от «красивой витрины» — хороший задел под реальные заявки позже.

## 5. Главный вывод: проект нужно сделать «наполняемым»

Сейчас данные попадают в продукт тремя разными способами:

| Тип данных | Где лежит сейчас | Как должно быть к наполнению |
| --- | --- | --- |
| Бренд (имя, tagline, лого) | Хардкод в Header/footer/titles | `site` / brand config или таблица `settings` |
| Каталог, цены, lead time | `data/atelier.ts` (+ дубль legacy) | Supabase `products` / `variants` (уже в схеме) |
| Фото | `/public/prototype`, старые `/photos_of_products` | Storage + URL в карточке товара; плейсхолдеры до съёмки |
| Адрес, часы, зоны доставки | Текст в страницах / дисклеймеры | `locations` / `fulfillment_rules` + UI empty-state |
| Контакты | Разрозненно / отсутствуют | `site.contacts` (LINE, email, phone) — пустые до утверждения |
| Переводы UI | Inline `t(ru,en,th)` в шаблонах | Словари i18n; контент товаров — поля locale в БД |
| База знаний | Демо keywords в `operations` + пустые `knowledge_documents` | Только БД + админка; чат читает published |
| Юр. / privacy | Почти нет | Статические MD/страницы или CMS, подключаются флагом |

**Принцип:** витрина рендерит **контракт** («покажи название бренда», «покажи список published товаров»). Пока значения пустые или `status=draft` — показываем аккуратный empty/coming-soon, а не выдуманный адрес.

## 6. Рекомендации (переориентированы под наполнение)

### 6.1. Каркас данных — P0

#### R1 · Единый «паспорт сайта» (brand & site settings)

**Зачем сейчас:** название бренда ещё не финально; его будут менять.  
**Что сделать:** один модуль/таблица `siteSettings`: `brandName`, `tagline`, `logoUrl`, `languages`, `demoMode`, `contacts{}`, `locationStatus: unknown|announced`.  
**Почему:** смена бренда = правка одной записи, а не 40 шаблонов. Wordmark в хедере и `<title>` читают оттуда же.

#### R2 · Каталог только через контракт БД (fixtures временно)

**Зачем сейчас:** товаров и цен нет — но схема уже есть.  
**Что сделать:**
1. Оставить `data/atelier.ts` как **seed/fixture** с пометкой `is_demo`.  
2. Витрину научить читать published-каталог из Supabase; если пусто — показать fixture **или** empty-state «коллекция готовится».  
3. Админке owner — формы создания товара/варианта/цены **до** того, как ассортимент утвердят (чтобы в день появления данных был куда писать).

**Почему:** когда появятся первые 3 реальных SKU, их внесут в админку без релиза фронта.

#### R3 · Цены: серверная модель готова раньше реальных цифр

**Сейчас приемлемо** принимать демо-цены с клиента.  
**До первых реальных цен** внедрить: intake по `variant_id`, цена только из БД.  
**Почему:** иначе в день «включили настоящие цены» откроется fraud-дыра. Каркас сверки делают **до** наполнения прайса, а не после.

#### R4 · Медиа-пайплайн без реальной съёмки

**Что сделать:** соглашение об ассетах — `Storage` bucket, поля `image_url`, alt на 3 языка, статус `concept|final`. Пока `concept` — подпись «концепт» (уже есть в духе прототипа). Удалить/изолировать 31 MB legacy-фото, чтобы не путать с будущим каталогом.  
**Почему:** фото появятся пакетами; нужна полка, а не папка `public/` в git навсегда.

#### R5 · Контакты и локация как данные со статусом

Не выдумывать адрес. Завести поля и UI:

- `location.announced = false` → «Адрес и дата открытия будут объявлены» (уже близко к текстам café/delivery).  
- Когда появятся — заполнить `address`, `mapsUrl`, `hours`, `lineId` без правки вёрстки.

**Почему:** страница delivery/contact/footer не должны переписываться при объявлении адреса.

#### R6 · База знаний: наполняемый конвейер, не документ «сразу»

Готового KB-документа нет — это нормально.  
**Что уже есть:** draft/publish, visibility, admin editor.  
**Что добавить к готовности наполнения:**
1. Чат витрины читает **только** published public из Supabase (не localStorage seed).  
2. Пока документов 0 — честный ответ «пока нет утверждённого ответа» + handoff (уже почти так).  
3. Шаблон brief для владельца: «как писать карточку знания» (короткий чеклист в `docs/`, не сам контент).

**Почему:** KB будут писать итеративно; AI подключать только после N утверждённых карточек.

#### R7 · Словари UI vs контент каталога

Inline `t(ru,en,th)` ок для прототипа UX, но для наполнения:

- **UI-строки** → файлы локалей (кнопки, ошибки, навигация).  
- **Бизнес-контент** (имя торта, описание, аллергены) → поля в БД на locale.  

Иначе переводчики и кондитеры правят одни и те же Vue-файлы.

#### R8 · Убрать ложные источники данных (legacy)

Вынести/удалить из активной ветки старый `products.ts`, Prisma-путь, неиспользуемые компоненты, zip.  
**Почему для наполнения:** иначе реальные товары могут случайно попасть не в ту модель.

### 6.2. Сценарии и продукт — P1 (можно делать без финального бренда)

#### R9 · Feature flag `demoMode` / `contentMode`

Управление дисклеймерами, demo-bar, ссылкой на `/demo-admin`, текстом «тестовая заявка».  
Когда данные появятся и бета закроется — один флаг, а не охота по строкам.

#### R10 · Empty-states на всех контентных поверхностях

Каталог пуст / KB пуста / контакты не объявлены / доставка «условия позже» — единый визуальный паттерн.  
Сейчас часть страниц уже честная; довести до системы, чтобы наполнение включало блоки «сами».

#### R11 · Партнёрская и контактная формы — контракт заявки без CRM

Форма cooperation сейчас noop — для прототипа ок.  
К наполнению: тот же intake-канал `enquiry_type: partner|contact|order` в БД (даже если менеджер один). Не обязательно LINE в первый день.

#### R12 · Одна корзина, два контура админки с ясными ролями

- `/demo-admin` — песочница обучения UX.  
- `/admin` — место, куда попадут **реальные** (и тестовые с `is_demo`) данные.  

Не сливать, пока нет контента; документировать «куда писать, когда пойдут данные».

#### R13 · Handoff чата → `conversations` в БД

Даже без LINE: кнопка «человек» создаёт запись, видимую в `/admin`.  
**Зачем до KB:** первые недели отвечать будет человек; KB накопится из реальных вопросов.

#### R14 · i18n routing позже, словари раньше

Префиксы `/en` `/th` — ближе к публичному запуску.  
Словари UI — раньше, чтобы утверждение брендовых формулировок не блокировалось вёрсткой.

#### R15 · Декомпозиция `admin` / `Chat` / CSS

Чтобы формы наполнения каталога и KB добавлять без боли в монолитных SFC.

---

### 6.3. Запуск — P2 (после появления данных)

Делать **когда** будут утверждены бренд, хотя бы стартовый ассортимент, канал связи и политика данных:

- SEO index, OG, JSON-LD (только на реальных Offer)  
- Cookie/PDPA, privacy page  
- Платежи + idempotent webhooks  
- LINE / Calendar dispatcher (jobs `held` уже задуманы)  
- Native review TH  
- CI e2e на критический путь  
- Owner activation и боевые staff-аккаунты  

**Не** блокировать прототип этими пунктами сейчас.

## 7. Прогноз развития (с учётом отсутствия данных)

### Фаза A — «Полка для данных» (сейчас, без ожидания бренда/цен)

Цель: можно начать вносить данные в любой момент, не ломая UX.

1. Паспорт сайта (R1) + флаги (R9)  
2. Витрина ↔ Supabase catalog + fixtures fallback (R2)  
3. Медиа-конвенция и чистка legacy-ассетов (R4, R8)  
4. Контакты/локация со статусом (R5)  
5. Чат ← published KB из БД; пустой KB = честный empty (R6)  
6. Короткие гайды наполнения для владельца (бренд, SKU, KB-карточка)  
7. Минимальный typecheck/CI, чтобы каркас не разъезжался  

**Результат фазы:** появился логотип / 3 товара / LINE — внесли через admin/settings, сайт обновился.

### Фаза B — «Закрытая бета с частичным контентом»

Когда есть черновой бренд и первые SKU (цены могут быть provisional):

1. Серверные цены по `variant_id` (R3)  
2. Реальные заявки с пометкой статуса подтверждения менеджером  
3. Staff accounts, наполнение KB по мере FAQ  
4. Словари UI + native pass по ключевым TH-строкам  
5. Формы partner/contact в БД (R11)  

**Результат:** можно показывать избранным партнёрам/друзьям без стыда за «фейковый адрес», но ещё без публичного SEO.

### Фаза C — «Наполнение → публичный soft-launch»

Когда утверждены название, стартовое меню, фото, канал связи, базовые условия получения:

1. Снять/ослабить demo-chrome флагом  
2. Индексация, аналитика с consent  
3. Оплата или явный offline-payment  
4. LINE/Calendar по необходимости  
5. AI только поверх утверждённой KB  

**Результат:** прототипская оболочка становится сайтом без rewrite.

## 9. Чеклист «готовы принимать реальные данные»

Отмечать **до** появления контента, не вместо него:

- [ ] Бренд/tagline/лого читаются из одного settings  
- [ ] Товар создаётся в admin → виден на витрине без деплоя кода  
- [ ] Цена для заявки берётся из БД (к моменту первых реальных цен)  
- [ ] Фото грузятся в Storage, в git не копим исходники пачками  
- [ ] Адрес/контакты: поля есть, пустые значения дают корректный UI  
- [ ] KB: draft → publish → чат видит только published  
- [ ] `demoMode` выключается одним флагом  
- [ ] Legacy-каталог РФ не пересекается с путём наполнения  
- [ ] Есть короткая инструкция владельцу: «куда класть бренд / SKU / FAQ»  

Чеклист публичного запуска (оплата, SEO, юр. тексты) — отдельный, **после** наполнения.

```

        │
        ▼
┌───────────────────┐
│ Settings · Catalog │  ← бренд, SKU, цены, фото, контакты, KB

          │ published only
```

`/demo-admin` остаётся слева от схемы — учебный стенд, не путь наполнения.

## 11. Итог

Прототип **оценён правильно именно как прототип**: отсутствие бренда, каталога, цен, фото, адреса, контактов и готовой KB — это исходные условия, а не провал.  

Ценность следующих работ — **сделать полки и краны**: settings, catalog admin, media, contacts-with-status, KB publish pipeline, флаги демо. Тогда появление данных превращается в операцию наполнения, а не в новый проект.

Развитие: **Фаза A (полки) → Фаза B (частичный контент + жёсткие цены) → Фаза C (публичный запуск)**. Переписывать Nuxt с нуля не требуется.
